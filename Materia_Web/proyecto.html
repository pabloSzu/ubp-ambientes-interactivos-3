Descripción

¿Qué es este proyecto?

Un juego de trivia donde cada jugador es un hilo — y con suficientes jugadores, el sistema se rompe de formas muy predecibles.

Thread-per-client

Cada jugador que se conecta genera un nuevo Thread. Con 20 jugadores → 20 hilos corriendo en paralelo, todos accediendo al mismo estado compartido.

Race conditions reales

El puntaje se guarda en un HashMap sin sincronización. Con un jugador, funciona perfecto. Con 10+, los puntajes se corrompen de forma no determinística.

Protocolo TCP de texto

Comunicación por sockets TCP. Una línea por mensaje. Podés conectarte con nc localhost 9000 desde la terminal y jugar manualmente.

Medible y mejorable

Tiene un script de stress test en Python que lanza N jugadores simultáneos y detecta automáticamente si los puntajes son inconsistentes.

Race conditions plantadas

Los tres bugs

Están en el código con comentarios que explican el problema. Tu trabajo es entenderlos y corregirlos.

Bug 1 ScoreBoard.java · addPoints() ALTA

El puntaje se guarda en un HashMap. El método addPoints() hace un read → modify → write en dos operaciones separadas. Entre esas dos operaciones, otro hilo puede leer el valor viejo.

ScoreBoard.java — código con bug
public void addPoints(String player, int points) {
    int current = scores.getOrDefault(player, 0); // Paso 1: leer
    scores.put(player, current + points);           // Paso 2: escribir
    // ← Entre estos dos pasos, Hilo B puede leer el mismo valor viejo
    //   y sobrescribir el resultado de Hilo A. Se pierde un incremento.
}
Traza del bug con 2 hilos simultáneos:
TiempoHilo A (María)Hilo B (Juan)scores["María"]
t=0lee current = 500—500
t=1—lee current = 500 ⚠500
t=2escribe 800—800
t=3—escribe 800 ⚠800
—Esperado: 1100 · Real: 800 · Pérdida: 300 puntos
Posibles correcciones:
synchronized en el método
ConcurrentHashMap + merge()
AtomicInteger por jugador
Bug 2 GameState.java · claimFirstAnswer() MEDIA

volatile garantiza que el valor sea visible entre hilos, pero no garantiza atomicidad del patrón check-then-act. Dos hilos pueden leer false simultáneamente antes de que ninguno escriba true.

GameState.java — código con bug
private volatile boolean firstAnswerClaimed = false;

public boolean claimFirstAnswer() {
    if (!firstAnswerClaimed) {      // Hilo A y B leen false a la vez
        firstAnswerClaimed = true;  // Ambos escriben true
        return true;                // Ambos retornan true → DOS "primeros"
    }
    return false;
}
Posibles correcciones:
synchronized en el método
AtomicBoolean.compareAndSet(false, true)
Bug 3 TriviaServer.java · lista clients BAJA

ArrayList no es thread-safe. Si un jugador se desconecta (llama a removeClient()) mientras otro hilo está iterando en broadcast(), se lanza una ConcurrentModificationException.

TriviaServer.java — código con bug
// Hilo principal agrega clientes
clients.add(handler);

// Hilo de broadcast itera la lista
for (ClientHandler c : clients) { c.send(message); }

// Hilo de un cliente que se desconecta modifica la lista
clients.remove(handler); // ← ConcurrentModificationException
Posibles correcciones:
CopyOnWriteArrayList
Collections.synchronizedList() + sync en iteración

Antes de arrancar

Tips para encarar el proyecto

El proyecto tiene 4 etapas que se apoyan una en la otra. No saltés a la Etapa 04 sin haber pasado por las anteriores — cada etapa te da el contexto que necesitás para la siguiente.

Antes de tocar cualquier código, leé los 5 archivos fuente. Tomá nota de qué hace cada clase y cómo se relacionan. Este paso ahorra horas de debugging después.
Usá IA para generar el boilerplate de la GUI (Swing/JavaFX) — es la parte más lenta si la escribís a mano. Pero en la presentación final te preguntamos por cualquier línea. Entendé cada pieza antes de entregarla.
División recomendada: una persona maneja la lógica del servidor y la concurrencia; la otra maneja la interfaz y la documentación. Ambos entienden todo, pero cada uno es dueño de su parte.
Usá el stress_test.py como tu detector de bugs permanente. Correlo después de cada cambio significativo — así sabés inmediatamente si rompiste algo o si lo corregiste.

Preguntas frecuentes

¿Por qué Java puro y no Spring Boot?

Para que el threading sea visible directamente. Con Spring Boot la concurrencia está oculta en el framework — acá la ven en el código.

¿El stress test no muestra el bug?

Las race conditions son no-determinísticas. Probá con --players 30 y --delay 0. En máquinas multicore el bug aparece más frecuentemente.

¿Puedo hacer una interfaz gráfica?

Sí. El protocolo es texto plano sobre TCP — podés conectar cualquier cliente: Swing, JavaFX, o incluso una página web. Bonus points garantizados.

¿Puedo usar IA para ayudarme?

Sí. Claude, ChatGPT, lo que quieran. Pero en la presentación te preguntamos por cualquier línea del código — asegurate de entender todo lo que entregás.
