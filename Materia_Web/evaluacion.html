Simulación concurrente en Java

10 pts

Implementá un programa Java que simule el siguiente escenario:

El banco concurrente

Un banco tiene N cajeros (hilos). Cada cajero atiende a clientes de una cola compartida. Cada atención dura entre 100 y 500 ms (simulado con Thread.sleep()). Cuando no hay clientes, los cajeros esperan. Cuando llega un cliente, el primer cajero disponible lo atiende.

Esqueleto para arrancar — BancoConcurrente.java · completá los // TODO
import java.util.concurrent.*;

public class BancoConcurrente {
    static final BlockingQueue<Integer> cola = new LinkedBlockingQueue<>();

    public static void main(String[] args) throws InterruptedException {
        final int CAJEROS = 3, CLIENTES = 15;
        for (int i = 1; i <= CLIENTES; i++) cola.add(i);   // cargar la cola

        Thread[] cajeros = new Thread[CAJEROS];
        for (int c = 0; c < CAJEROS; c++) {
            cajeros[c] = new Thread(() -> {
                Integer cliente;
                while ((cliente = cola.poll()) != null) {  // poll() es atómico (thread-safe)
                    int ms = 100 + (int)(Math.random() * 400);   // 100..500 ms
                    // TODO 1: simular la atención con Thread.sleep(ms)
                    // TODO 2: loguear "Cajero X atendió al cliente Y en Z ms"
                    //          (usá Thread.currentThread().getName())
                }
            }, "Cajero-" + (c + 1));
        }
        // TODO 3: arrancar todos los cajeros (start) y después esperarlos (join)
        // Parte B (versión ROTA): reemplazá la BlockingQueue por un índice
        //   compartido sin sincronizar (int siguiente;) para que dos cajeros
        //   tomen el mismo cliente. Mostrá el bug con el log.

Versión funcional

Código Java que funcione con al menos 3 cajeros y 15 clientes. El log debe mostrar qué cajero atiende a qué cliente y cuánto tardó. Usá Thread.currentThread().getName() para identificar los hilos.

Modificá el código para que dos cajeros puedan tomar el mismo cliente de la cola (quitá la sincronización correcta). Mostrá con evidencia (log de ejecución) que el bug ocurre.

Pipeline IPC: productor-consumidor

10 pts

Implementá el patrón Productor-Consumidor en Java usando BlockingQueue. El sistema simula un pipeline de procesamiento de datos en tiempo real.

El pipeline de sensores

Dos productores generan lecturas de sensores (ID único + valor + timestamp). Tres consumidores procesan las lecturas y registran el tiempo de procesamiento. La cola tiene capacidad máxima de 10 elementos.

Esqueleto para arrancar — PipelineSensores.java · completá los // TODO
import java.util.concurrent.*;

public class PipelineSensores {
    record Lectura(int id, double valor, long ts) {}

    public static void main(String[] args) {
        BlockingQueue<Lectura> cola = new LinkedBlockingQueue<>(10);  // capacidad 10

        for (int p = 1; p <= 2; p++) {            // 2 PRODUCTORES
            final int pid = p;
            new Thread(() -> {
                for (int i = 0; i < 20; i++) {
                    Lectura l = new Lectura(i, Math.random()*100, System.currentTimeMillis());
                    // TODO 1: cola.put(l)  → bloquea si la cola está LLENA
                    // TODO 2: loguear "Productor " + pid + " generó id=" + i
                    // Parte B: bajá el sleep del productor para que genere ~3x más rápido
                }
            }, "Productor-" + p).start();
        }

        for (int c = 1; c <= 3; c++) {            // 3 CONSUMIDORES
            final int cid = c;
            new Thread(() -> {
                try {
                    while (true) {
                        // TODO 3: Lectura l = cola.take()  → bloquea si está VACÍA
                        // TODO 4: simular procesamiento (Thread.sleep) y loguear
                        //          "Consumidor " + cid + " procesó id=" + l.id()
                    }

            }, "Consumidor-" + c).start();
        }
    }
}

B  ·  3 pts
Experimento de saturación

Modificá los tiempos para que los productores generen datos 3 veces más rápido que lo que los consumidores pueden procesar. ¿Qué pasa con la cola? ¿El programa se bloquea? ¿Por qué? Mostrá con evidencia.

Diagrama y análisis

Dibujá el diagrama de flujo de la comunicación entre hilos (puede ser a mano y fotografiado). Luego explicá: ¿en qué se diferencia esta solución de una solución con wait()/notify()? ¿Cuándo usarías cada una?

Entregables

  • Código Java funcional con los 2 escenarios (normal y saturado)
  • Log de ejecución de ambos escenarios

BlockingQueue.put() bloquea si la cola está llena. BlockingQueue.take() bloquea si está vacía. No necesitás ningún synchronized extra — la cola ya lo maneja internamente.

El problema de los filósofos — de roto a correcto

20 pts

Implementá el clásico Problema de los Filósofos Comensales en dos versiones: primero la versión naive que produce deadlock, después una versión corregida que lo previene.

El escenario

5 filósofos sentados en una mesa circular. Entre cada par de filósofos hay un tenedor. Para comer, cada filósofo necesita los dos tenedores a sus lados. Cuando no come, piensa.

Esqueleto para arrancar — Filosofos.java · ya viene la versión ROTA; completá la corrección
import java.util.concurrent.Semaphore;

public class Filosofos {
    static final int N = 5;
    static final Semaphore[] tenedores = new Semaphore[N];

    public static void main(String[] args) {
        for (int i = 0; i < N; i++) tenedores[i] = new Semaphore(1);
        for (int i = 0; i < N; i++) {
            final int id = i;
            new Thread(() -> filosofo(id), "Filosofo-" + id).start();
        }
    }

    static void filosofo(int id) {
        int izq = id, der = (id + 1) % N;
        try {
            while (true) {
                Thread.sleep((long)(Math.random() * 100));   // pensar

                // Parte A (ROTA): toma SIEMPRE izquierdo y luego derecho → deadlock
                tenedores[izq].acquire();
                Thread.sleep(10);                 // ← da tiempo a que se cuelgue
                tenedores[der].acquire();

                System.out.println("Filósofo " + id + " COME");
                Thread.sleep((long)(Math.random() * 100));   // comer

                // TODO: soltar ambos tenedores (tenedores[izq].release(), ...[der].release())

                // Parte B (CORREGIDA): aplicá UNA estrategia para evitar el deadlock:
                //   · jerarquía de recursos: tomar primero el tenedor de MENOR id
                //   · semáforo de sala: solo N-1 filósofos intentan comer a la vez
            }
        } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }
}

Parte A — La versión rota 8 pts

A1  ·  3 pts
Implementación naive

Cada filósofo intenta tomar el tenedor izquierdo primero y después el derecho. Usá Semaphore(1) para cada tenedor. El programa debe colgarse con la cantidad correcta de filósofos.

A2  ·  3 pts
Evidencia del deadlock

Capturá el momento en que el programa se cuelga (log de consola, jstack o diagrama de estado). Explicá en qué estado quedó cada hilo.

A3  ·  2 pts
Condiciones de Coffman

Identificá cuáles de las 4 condiciones de Coffman están presentes en tu implementación rota. Sé específico: ¿cuál es el recurso retenido? ¿Quién espera a quién?

Parte B — La versión corregida 12 pts

B1  ·  5 pts
Implementación de UNA estrategia de prevención

Elegí e implementá una de las siguientes:

  • Filósofo asimétrico: el último filósofo toma los tenedores en orden inverso
  • Semáforo de sala: solo N-1 filósofos pueden intentar comer simultáneamente
  • Jerarquía de recursos: siempre tomar el tenedor de menor ID primero
B2  ·  4 pts
Demostración de correctitud

Ejecutá el programa durante al menos 10 ciclos completos de comer por filósofo y mostrá que ningún hilo se bloquea indefinidamente. El log debe mostrar que todos los filósofos eventualmente comen.

B3  ·  3 pts
Análisis de starvation

¿Puede haber starvation en tu solución (un filósofo que nunca come aunque no hay deadlock)? Si sí, ¿cómo lo detectarías? ¿Cómo lo prevendrías? Si no, ¿por qué no?

Entregables

  • Código Java de la versión rota + evidencia del deadlock (log o captura)
  • Código Java de la versión corregida + log de 10 ciclos por filósofo
  • Documento con análisis de Coffman y análisis de starvation

Para que el deadlock aparezca más fácil, podés agregar Thread.sleep(10) entre tomar el tenedor izquierdo y el derecho. Así el scheduler tiene más chances de intercalar los hilos en el momento exacto.
