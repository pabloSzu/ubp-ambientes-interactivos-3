📞 IPC

Inter-Process Communication. Cómo dos procesos separados se hablan, ya que cada proceso tiene su propia memoria y no puede ver la del otro.

Como dos personas en habitaciones cerradas: no se pueden tocar, pero pueden hablar por teléfono, pasar notas por debajo de la puerta, o escribir en una pizarra compartida.
🚿 Pipe

Tubería de datos unidireccional. Lo que A escribe, B lo lee. Los datos van en orden de llegada.

Como una fila de supermercado: primero en entrar, primero en salir. A pone datos, B los saca en el mismo orden.
📮 Cola de mensajes

Un buzón compartido entre procesos. A deja mensajes, B los recoge cuando puede. No necesitan estar sincronizados.

Como el correo: mandás la carta (no esperás a que el otro la abra), el otro la lee cuando quiere.
🧠 Memoria compartida

El método más rápido: los dos procesos leen y escriben en el mismo bloque de RAM. Sin un lock, es una race condition garantizada.

Como una pizarra que los dos pueden ver y modificar al mismo tiempo. Muy rápido, pero sin reglas es un caos.
🔌 Socket

Comunicación a través de la red entre procesos. Pueden estar en la misma máquina o en otras.

Como llamar por teléfono a otro proceso. Da igual si está al lado tuyo o en otro país.

IPC es cómo hablan los procesos entre sí. Pipe es tubería ordenada. Cola de mensajes es el buzón. Memoria compartida es la pizarra común. Socket es el teléfono entre procesos.

El problema del aislamiento

¿Por qué necesitan comunicarse?

El diseño del sistema operativo aisla los procesos entre sí: cada uno vive en su propia burbuja de memoria virtual. Sin IPC, dos procesos son islas incomunicadas.

PROCESO AISLADO

La isla

Sin mecanismo de IPC, cada proceso es una isla. Tiene su propio espacio de memoria virtual — no puede leer ni escribir la memoria de otro proceso. El SO lo garantiza por seguridad.

Espacio de memoria propio (aislado)
Stack Solo accesible por este proceso
Heap Invisible para los demás
  • Fallo aislado — no afecta a otros procesos
  • Seguridad — no puede espiar otros procesos
  • No puede intercambiar datos directamente
  • Necesita IPC para coordinarse
IPC
PROCESO COMUNICADO

El canal

Con un mecanismo de IPC, los procesos tienen un canal controlado para intercambiar datos. El SO actúa de intermediario — garantiza que la comunicación sea segura y ordenada.

Proceso A
pipe / cola / shm
Proceso B
  • Intercambio de datos controlado
  • Sincronización automática (colas)
  • Sin acceso directo a la memoria ajena
  • Overhead de IPC (copias, locks, syscalls)
Las herramientas del SO

Los 4 mecanismos de IPC

Cada mecanismo tiene su nicho: velocidad, persistencia, acoplamiento y complejidad distintos. Elegir el correcto es decisión de diseño, no de implementación.

Pipe
Velocidad
3/4

Canal de comunicación unidireccional entre dos procesos relacionados. Los datos fluyen de escritor a lector como una tubería — lo que entra primero sale primero.

Caso de uso: filtros Unix, child_process
  • Simple y rápido
  • Buffering automático por el SO
  • Solo entre padre-hijo (fork)
  • Unidireccional
FIFO / Named Pipe
Velocidad
3/4

Como un pipe, pero con nombre en el filesystem. Cualquier proceso que conozca el path puede abrirlo, sin relación padre-hijo.

Caso de uso: demonios, logger de sistema
  • Procesos no relacionados pueden comunicarse
  • Persiste en el filesystem
  • Sigue siendo unidireccional
  • Requiere un path conocido
Cola de mensajes
Velocidad
2/4

Estructura asincrónica: el productor envía mensajes y sigue su camino aunque el consumidor esté caído. Los mensajes esperan hasta ser procesados.

Caso de uso: sistemas de pedidos, event queues
  • Asincrónica y desacoplada
  • Persistente — mensajes sobreviven caídas
  • Mayor overhead que pipe
  • Requiere gestión del broker
Memoria compartida
Velocidad
4/4

El mecanismo más rápido: ambos procesos mapean el mismo segmento físico de RAM. Sin copia de datos — pero requiere sincronización manual (mutex, semáforo).

Caso de uso: rendering 3D, IA, tiempo real
  • Sin copia — latencia mínima
  • Ideal para datos grandes y alta frecuencia
  • Requiere sincronización manual
  • Race conditions si se usa mal

import java.util.concurrent.*;

public class ProductorConsumidor {
    // Queue con capacidad máxima 5 — put() bloquea si está llena, take() bloquea si está vacía
    private static final BlockingQueue<String> queue = new LinkedBlockingQueue<>(5);

    public static void main(String[] args) throws InterruptedException {
        Thread productor = new Thread(() -> {
            for (int i = 1; i <= 10; i++) {
                try {
                    String item = "Item-" + i;
                    queue.put(item);  // BLOQUEA si queue llena — espera automáticamente
                    System.out.println("[P] Produjo: " + item + " | En cola: " + queue.size());
                    Thread.sleep(200);
                } catch (InterruptedException e) { Thread.currentThread().interrupt(); return; }
            }
        }, "Productor");

        Thread consumidor = new Thread(() -> {
            for (int i = 0; i < 10; i++) {
                try {
                    String item = queue.take(); // BLOQUEA si queue vacía — espera automáticamente
                    Thread.sleep(500); // simula procesamiento más lento que producción
                    System.out.println("[C] Consumió: " + item + " | En cola: " + queue.size());
                } catch (InterruptedException e) { Thread.currentThread().interrupt(); return; }
            }
        }, "Consumidor");

        productor.start();
        consumidor.start();
        productor.join();
        consumidor.join();
        System.out.println("Pipeline completo. Total en cola: " + queue.size());
    }
}
¿Cuándo usarlo?

El patrón básico de productor-consumidor con un solo par. LinkedBlockingQueue(5) es el buffer. El productor genera más rápido que el consumidor — la queue actúa como amortiguador y bloquea al productor cuando se llena. No necesitás sincronización manual.

import java.util.concurrent.*;

public class Pipeline3Etapas {
    // Queues de comunicación entre etapas
    static final BlockingQueue<String> etapa1a2 = new LinkedBlockingQueue<>(3);
    static final BlockingQueue<String> etapa2a3 = new LinkedBlockingQueue<>(3);

    public static void main(String[] args) throws InterruptedException {
        // Etapa 1: Generador — produce datos crudos
        Thread etapa1 = new Thread(() -> {
            for (int i = 1; i <= 5; i++) {
                try {
                    String raw = "dato-" + i;
                    etapa1a2.put(raw);
                    System.out.println("[E1-GENERA]  → " + raw);
                    Thread.sleep(300);
                } catch (InterruptedException e) { Thread.currentThread().interrupt(); return; }
            }
        }, "Generador");

        // Etapa 2: Procesador — transforma los datos
        Thread etapa2 = new Thread(() -> {
            for (int i = 0; i < 5; i++) {
                try {
                    String raw = etapa1a2.take();
                    String processed = raw.toUpperCase() + "_OK";
                    etapa2a3.put(processed);
                    System.out.println("[E2-PROCESA] → " + processed);
                    Thread.sleep(500);
                } catch (InterruptedException e) { Thread.currentThread().interrupt(); return; }
            }
        }, "Procesador");

        // Etapa 3: Consumidor — entrega el resultado final
        Thread etapa3 = new Thread(() -> {
            for (int i = 0; i < 5; i++) {
                try {
                    String result = etapa2a3.take();
                    System.out.println("[E3-ENTREGA] → " + result + " ✓");
                    Thread.sleep(200);
                } catch (InterruptedException e) { Thread.currentThread().interrupt(); return; }
            }
        }, "Consumidor");

        long inicio = System.currentTimeMillis();
        etapa1.start(); etapa2.start(); etapa3.start();
        etapa1.join(); etapa2.join(); etapa3.join();
        System.out.println("Pipeline completado en " + (System.currentTimeMillis() - inicio) + "ms");
    }
}
Esta es la Actividad

Pipeline de 3 etapas conectadas por BlockingQueues. Cada etapa es un hilo independiente. Las colas actúan como buffers entre etapas — si una etapa es más lenta, la cola la desacopla temporalmente. Este es el patrón que vas a implementar y medir en la actividad práctica.

import java.io.*;

public class PipedStreamDemo {
    public static void main(String[] args) throws IOException, InterruptedException {
        // PipedOutputStream y PipedInputStream — simulan el pipe del sistema operativo
        PipedOutputStream pipeOut = new PipedOutputStream();
        PipedInputStream  pipeIn  = new PipedInputStream(pipeOut, 1024);

        // Escritor: escribe en el extremo de salida del pipe
        Thread escritor = new Thread(() -> {
            try (PrintWriter writer = new PrintWriter(new OutputStreamWriter(pipeOut))) {
                for (int i = 1; i <= 5; i++) {
                    writer.println("Mensaje " + i);
                    writer.flush();
                    System.out.println("[PIPE→] Escribió: Mensaje " + i);
                    Thread.sleep(400);
                }
            } catch (Exception e) { e.printStackTrace(); }
        }, "Escritor");

        // Lector: lee del extremo de entrada del pipe
        Thread lector = new Thread(() -> {
            try (BufferedReader reader = new BufferedReader(new InputStreamReader(pipeIn))) {
                String linea;
                while ((linea = reader.readLine()) != null) {
                    System.out.println("[→PIPE] Leyó:    " + linea);
                }
            } catch (IOException e) { e.printStackTrace(); }
        }, "Lector");

        escritor.start();
        lector.start();
        escritor.join();
        lector.join();
        System.out.println("Pipe cerrado. Comunicación completa.");
    }
}
El equivalente Java al pipe Unix

PipedOutputStream/PipedInputStream simulan el pipe del SO dentro de la JVM. El escritor conecta su salida a la entrada del lector — datos unidireccionales, bloqueante. Útil para entender el concepto, pero en producción se prefiere BlockingQueue por más control y flexibilidad.

El patrón fundamental

El problema Productor-Consumidor

Cuando un productor y un consumidor corren a velocidades distintas, la queue actúa como amortiguador. Pero tiene límite — y ahí aparece el backpressure.

Equilibrio
P = C · Productor y consumidor van a la misma velocidad. La queue se mantiene estable — ni se llena ni se vacía.
Queue estable
Productor más rápido
P > C · La queue se va llenando. Cuando está llena, el productor se bloquea — put() espera que el consumidor libere un slot.
Productor BLOQUEADO
Consumidor más rápido
P < C · La queue se vacía. El consumidor llama take() y se bloquea esperando que el productor agregue algo.
Consumidor ESPERANDO

El patrón que lo une todo

Programación orientada a eventos — el event loop

IPC te enseña cómo los procesos se comunican. Los eventos te enseñan cuándo reaccionan. Todo sistema interactivo — desde un videojuego hasta una app web — funciona con un loop que espera eventos y los despacha al handler correcto.

El Event Loop

Un loop infinito que hace tres cosas: espera eventos, desencola el siguiente, y ejecuta el handler correspondiente. Mientras no hay eventos: duerme (sin consumir CPU). Cuando llega uno: actúa.

Polling

El proceso pregunta activamente: "¿hay algo nuevo?" en un loop. Consume CPU aunque no haya nada. Simple de implementar.

while(true) { if (hayDatos()) procesá(); }
vs
Event-driven

El proceso duerme. El SO lo despierta cuando llega un evento. CPU = 0% en espera. Escala a miles de conexiones.

selector.select(); // bloquea hasta evento
Event Loop — flujo completo
1
Esperar — el proceso bloquea en select() / epoll_wait() hasta que el SO avise
2
Detectar — el SO devuelve qué eventos ocurrieron (datos listos, conexión nueva, timeout)
3
Despachar — para cada evento, llamar al handler registrado (callback, listener, handler)
4
Ejecutar — el handler procesa el evento y puede generar nuevos eventos en la cola
volver al paso 1
Patrones event-driven en Java
Observer

Listener / Observer

Un objeto emite eventos; otros se suscriben para recibirlos. El emisor no sabe quién escucha — bajo acoplamiento.

button.addActionListener(e -> {
  System.out.println("click!");
});
Future

CompletableFuture

Operación asincrónica que "completa" en el futuro. Se encadenan operaciones sin bloquear el hilo principal.

CompletableFuture
  .supplyAsync(() -> fetchData())
  .thenApply(data -> process(data))
  .thenAccept(result -> show(result));
NIO

Java NIO + Selector

Un solo hilo maneja miles de conexiones simultáneas con I/O no bloqueante. El modelo de Node.js, pero en Java.

Selector sel = Selector.open();
channel.register(sel, OP_READ);
while (true) {
  sel.select();        // espera eventos
  for (SelectionKey k : sel.selectedKeys()) {
    if (k.isReadable()) handleRead(k);
  }
}
Conexión con IPC

Los eventos son IPC con semántica temporal. Un pipe o socket entrega datos — el event loop decide cuándo procesarlos y qué código ejecutar. Son capas complementarias: IPC es el canal, el event loop es el despachador.

Vocabulario técnico

Glosario

Tocá cada tarjeta para ver la definición. Estos son los términos que vas a usar al diseñar sistemas distribuidos, microservicios y pipelines de datos.

IPC Tocá

Inter-Process Communication. Mecanismos del SO para que procesos aislados intercambien datos. Los procesos no comparten memoria por defecto, por eso necesitan IPC. Categorías: memoria compartida, paso de mensajes, señales.

Pipe Tocá

Canal de comunicación unidireccional entre procesos. El productor escribe en un extremo, el consumidor lee del otro. FIFO (First In, First Out). Pipes anónimos: solo entre procesos padre-hijo. Named pipes (FIFO): entre cualquier proceso.

FIFO Tocá

First In, First Out. Política de orden en la que el primer dato en entrar es el primero en salir. Garantiza orden en la entrega de mensajes. Todos los pipes son FIFO por naturaleza.

Cola de mensajes Tocá

Estructura IPC que permite a procesos intercambiar mensajes discretos y tipados. El receptor puede filtrar mensajes por tipo. Persiste aunque el proceso receptor no esté activo.

Memoria compartida Tocá

El mecanismo IPC más rápido: múltiples procesos mapean el mismo bloque de memoria física en sus espacios virtuales. Sin sincronización explícita (mutex/semáforo) es una race condition garantizada.

Socket Tocá

Endpoint de comunicación bidireccional entre procesos, local o remoto. TCP socket: confiable, ordenado. UDP socket: rápido, sin garantía de entrega. Base de toda comunicación de red.

BlockingQueue Tocá

Cola thread-safe en Java (java.util.concurrent) que bloquea al productor si está llena y al consumidor si está vacía. Implementa el patrón productor-consumidor sin manejo manual de locks.

Señal (Signal) Tocá

Notificación asíncrona enviada a un proceso por el SO o por otro proceso. SIGINT (Ctrl+C), SIGKILL, SIGTERM. El proceso puede capturar señales con handlers o ignorarlas (excepto SIGKILL).

Serialización Tocá

Convertir un objeto en memoria a un formato que puede enviarse por un canal IPC (bytes, JSON, XML). El receptor deserializa para reconstruir el objeto. Imprescindible en comunicación entre procesos.

Productor-Consumidor Tocá

Patrón de diseño clásico de concurrencia: un proceso produce datos, otro los consume. Se resuelve con una cola compartida. El desafío: sincronizar sin deadlock ni race condition.
