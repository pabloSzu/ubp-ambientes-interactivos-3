La unidad de ejecución

Proceso vs Hilo: ¿cuál es la diferencia?

Entender qué comparte y qué aisla cada unidad de ejecución es el punto de partida de cualquier análisis serio de concurrencia.

PROCESO

Unidad aislada

Un proceso es una instancia de programa con su propio espacio de memoria. Tiene todo lo que necesita: código, datos, heap y stack independiente. Si falla, no arrastra a los demás.

NEW

El hilo fue creado con new Thread() pero start() no fue llamado. Existe en memoria pero no tiene tiempo de CPU asignado.

RUNNABLE

Listo para correr. Puede estar ejecutándose o esperando su turno de CPU. El scheduler decide cuándo le toca.

BLOCKED

Esperando adquirir un lock synchronized que otro hilo tiene. No consume CPU. Pasa a RUNNABLE cuando obtiene el lock.

WAITING / TIMED_WAITING

Esperando una condición externa: wait(), join() o sleep(ms). Sale cuando alguien llama notify() o vence el tiempo.

El bug más difícil de reproducir

Race Condition: cuando el orden importa

Una race condition ocurre cuando el resultado de un programa depende del orden de ejecución de los hilos — un orden que el programador no controla y el scheduler no garantiza.

El problema: Read-Modify-Write no es atómico
1
READ
Hilo lee counter = 5 desde memoria
2
MODIFY
Calcula 5 + 1 = 6 en su registro
3
WRITE
Escribe counter = 6 en memoria
Si otro hilo hace READ después del paso 1 pero antes del paso 3, ambos escriben 6. Se pierden incrementos. Con 3 hilos y 100 incrementos cada uno, el resultado debería ser 300 — pero no lo es.

El código con el bug
Race Condition
public class RaceCounter {
    static int counter = 0; // variable compartida, SIN sincronización

    public static void main(String[] args) throws InterruptedException {
        Thread t1 = new Thread(() -> {
            for (int i = 0; i < 100; i++) {
                counter++; // read → modify → write: NO es atómico
            }
        });
        Thread t2 = new Thread(() -> {
            for (int i = 0; i < 100; i++) {
                counter++; // otro hilo hace exactamente lo mismo
            }
        });
        Thread t3 = new Thread(() -> {
            for (int i = 0; i < 100; i++) {
                counter++; // y otro más
            }
        });

        t1.start(); t2.start(); t3.start();
        t1.join();  t2.join();  t3.join();

        // Debería ser 300. Casi nunca lo es.
        System.out.println("counter = " + counter);
    }
}
La sintaxis de la concurrencia

Tres formas de crear hilos en Java

Java evolucionó la API de hilos a lo largo de las versiones. Cada enfoque tiene su contexto ideal — saber cuál usar es parte del criterio profesional.

// Opción 1: Extender Thread
public class MiHilo extends Thread {
    private String nombre;

    public MiHilo(String nombre) {
        this.nombre = nombre;
    }

    @Override
    public void run() {
        // Este código corre en un hilo separado
        for (int i = 1; i <= 5; i++) {
            System.out.println(nombre + " → paso " + i);
            try {
                Thread.sleep(200); // simula trabajo
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                return;
            }
        }
    }
}

// En main():
MiHilo h1 = new MiHilo("Hilo-A");
MiHilo h2 = new MiHilo("Hilo-B");
h1.start(); // NO llamar run() — start() crea el hilo real
h2.start();
h1.join(); h2.join(); // esperar a que terminen
¿Cuándo usarlo?

Código educativo o scripts simples donde necesitás control total sobre el hilo. En producción, evitalo — extender Thread limita la herencia de otras clases y no escala bien.

// Opción 2: Implementar Runnable (preferida sobre Thread)
public class MiTarea implements Runnable {
    private String nombre;

    public MiTarea(String nombre) {
        this.nombre = nombre;
    }

    @Override
    public void run() {
        for (int i = 1; i <= 5; i++) {
            System.out.println(nombre + " → paso " + i +
                " [" + Thread.currentThread().getName() + "]");
        }
    }
}

// Con lambda (Java 8+) — más limpio y conciso
Runnable tarea1 = () -> {
    for (int i = 0; i < 5; i++) {
        System.out.println("Lambda hilo: " + i);
    }
};

Thread hilo1 = new Thread(new MiTarea("Worker-1"));
Thread hilo2 = new Thread(tarea1);

hilo2.start();

¿Cuándo usarlo?

Cuando la tarea es una unidad de trabajo discreta. Permite implementar otras interfaces al mismo tiempo. Las lambdas lo hacen muy conciso. Mejor que extender Thread — separa la tarea del mecanismo de ejecución.

// Opción 3: ExecutorService — el estándar en producción
import java.util.concurrent.*;

public class EjecutorDemo {
    public static void main(String[] args) throws Exception {
        // Pool de 4 hilos reutilizables
        ExecutorService executor = Executors.newFixedThreadPool(4);

        // Enviar tareas sin preocuparse por la gestión de hilos
        for (int i = 1; i <= 10; i++) {
            final int tarea = i;
            executor.submit(() -> {
                System.out.println("Tarea " + tarea +
                    " en " + Thread.currentThread().getName());
                return tarea * tarea;
            });
        }

        // Esperar a que todas las tareas terminen
        executor.shutdown();
        boolean terminado = executor.awaitTermination(10, TimeUnit.SECONDS);
        System.out.println("Completado: " + terminado);

        // Con Callable para obtener resultados tipados
        ExecutorService exec2 = Executors.newSingleThreadExecutor();
        Future<Integer> futuro = exec2.submit(() -> {
            Thread.sleep(500);
            return 42;
        });
        int resultado = futuro.get(); // bloquea hasta tener el valor
        System.out.println("Resultado: " + resultado);
        exec2.shutdown();
    }
}
¿Cuándo usarlo?

Siempre que sea posible en código real. Reutiliza hilos, controla el pool size, maneja excepciones correctamente y soporta Callable/Future para resultados. Es el estándar de la industria desde Java 5.

public class RaceConditionDemo {
    static int counter = 0;

    public static void main(String[] args) throws InterruptedException {
        int HILOS = 3;
        int INCREMENTOS = 1000;
        Thread[] threads = new Thread[HILOS];

        for (int t = 0; t < HILOS; t++) {
            final int id = t + 1;
            threads[t] = new Thread(() -> {
                for (int i = 0; i < INCREMENTOS; i++) {
                    counter++; // SIN sincronización — race condition aquí
                }
            }, "Thread-" + id);
        }

        long inicio = System.currentTimeMillis();
        for (Thread t : threads) t.start();
        for (Thread t : threads) t.join();
        long fin = System.currentTimeMillis();

        System.out.println("=== Race Condition Demo ===");
        System.out.println("Resultado: " + counter);
        System.out.println("Esperado:  " + (HILOS * INCREMENTOS));
        System.out.println("Diferencia: " + (HILOS * INCREMENTOS - counter));
        System.out.println("Tiempo: " + (fin - inicio) + "ms");

        if (counter == HILOS * INCREMENTOS) {
            System.out.println("Tuviste suerte esta vez. Corré de nuevo.");
        } else {
            System.out.println("Race condition confirmada. Se perdieron incrementos.");
        }
    }
}

Vocabulario técnico

Glosario

Tocá cada tarjeta para ver la definición. Estos son los términos que vas a usar en entrevistas técnicas, revisiones de código y diseño de sistemas concurrentes.

Proceso Tocá

Instancia de un programa en ejecución con su propio espacio de memoria aislado. Tiene código, heap, stack y recursos propios. El SO le asigna un PID único. Ej: cada pestaña del navegador es un proceso.

Hilo (Thread) Tocá

Unidad de ejecución dentro de un proceso. Comparte heap y código con otros hilos del mismo proceso pero tiene su propio stack. También llamado "proceso liviano". Java crea hilos con Thread o ExecutorService.

Scheduler Tocá

Componente del SO que decide qué hilo recibe tiempo de CPU y por cuánto tiempo. Java no controla al scheduler — el SO es el árbitro. Por eso el orden de ejecución de los hilos no está garantizado.

Concurrencia Tocá

Múltiples tareas en progreso simultáneo, intercaladas por el scheduler en uno o más cores. Es un concepto de diseño: el programa está estructurado para manejar múltiples tareas a la vez, aunque no corran exactamente al mismo tiempo.

Paralelismo Tocá

Ejecución verdaderamente simultánea de múltiples tareas en múltiples cores. Requiere hardware (más de 1 core) y software bien particionado. Un programa con un solo core puede ser concurrente pero nunca paralelo.

Race Condition Tocá

Bug donde el resultado de un programa depende del orden de ejecución de los hilos. Ocurre cuando dos o más hilos acceden y modifican datos compartidos sin sincronización. El resultado es impredecible y difícil de reproducir.

Context Switch Tocá

Operación del SO donde guarda el estado de un hilo (registros, stack pointer, program counter) y carga el estado de otro. Dura ~1000ns. Demasiados context switches pueden degradar el rendimiento más que el trabajo real.

ExecutorService Tocá

API de alto nivel de Java para gestionar pools de hilos. Reutiliza hilos en lugar de crear y destruir, controla el tamaño del pool, maneja excepciones y soporta Callable/Future para tareas con resultados. Estándar desde Java 5.

Antes de arrancar

¿Cómo se investiga una race condition?

Una race condition no es un error que se ve a simple vista. Aparece de forma intermitente, con valores incorrectos que varían entre ejecuciones. La clave es reproducirla consistentemente y luego corregirla con la herramienta de sincronización correcta.

En Java, la solución básica es synchronized. La solución de alto nivel es AtomicInteger del paquete java.util.concurrent.atomic. Ambas garantizan atomicidad del read-modify-write.
