La unidad de ejecución

Proceso vs Hilo: ¿cuál es la diferencia?

Entender qué comparte y qué aisla cada unidad de ejecución es el punto de partida de cualquier análisis serio de concurrencia.

PROCESO

Unidad aislada

Un proceso es una instancia de programa con su propio espacio de memoria. Tiene todo lo que necesita: código, datos, heap y stack independiente. Si falla, no arrastra a los demás.

Creación de procesos

fork() — El proceso hijo

¿Cómo nace un proceso en sistemas reales? Con la llamada al sistema fork(). Entender fork() es clave para comprender la diferencia real entre crear un proceso vs crear un hilo — y por qué el SO los trata tan distinto.

01
fork() — Clon del proceso padre

La syscall fork() crea un proceso hijo que es una copia exacta del padre: mismo código, mismo heap, misma pila, mismos archivos abiertos. Después del fork, dos procesos corren el mismo programa — pero de forma completamente independiente.

02
Valor de retorno — ¿quién soy?

La distinción entre padre e hijo la da el valor de retorno: fork() retorna 0 en el hijo y el PID del hijo en el padre. Así, el mismo código ejecuta cosas distintas según quién sea.

03
Copy-on-Write — el truco del SO

Aunque el hijo empieza con la misma memoria, los cambios que haga no afectan al padre. El SO usa Copy-on-Write: la copia real de memoria solo ocurre cuando alguno modifica los datos, minimizando el costo inicial de crear el proceso.

¿Por qué C? fork() es una syscall del kernel Unix — Java la oculta a propósito para ser multiplataforma. Este es el único bloque en C del módulo: lo usamos para ver qué pasa por debajo cuando el SO crea un proceso. En Java vas a usar ProcessBuilder para esto — Java nunca te expone fork() directamente.

fork() en C — la syscall POSIX
C / POSIX
#include <unistd.h>
#include <stdio.h>

int main() {
    int x = 10;         // variable antes del fork
    pid_t pid = fork(); // crea el proceso hijo

    if (pid == 0) {
        // --- Código del HIJO ---
        x = 20;   // solo modifica su copia (Copy-on-Write)
        printf("Soy el hijo.  PID=%d, x=%d\n", getpid(), x);
    } else {
        // --- Código del PADRE ---
        printf("Soy el padre. PID=%d, x=%d\n", getpid(), x);
        // x sigue siendo 10: el hijo no afecta al padre
    }
    return 0;
}

El bug más difícil de reproducir

Race Condition: cuando el orden importa

Una race condition ocurre cuando el resultado de un programa depende del orden de ejecución de los hilos — un orden que el programador no controla y el scheduler no garantiza.

El problema: Read-Modify-Write no es atómico
1
READ
Hilo lee counter = 5 desde memoria
2
MODIFY
Calcula 5 + 1 = 6 en su registro
3
WRITE
Escribe counter = 6 en memoria
Si otro hilo hace READ después del paso 1 pero antes del paso 3, ambos escriben 6. Se pierden incrementos. Con 3 hilos y 100 incrementos cada uno, el resultado debería ser 300 — pero no lo es.

El código con el bug
Race Condition
public class RaceCounter {
    static int counter = 0; // variable compartida, SIN sincronización

    public static void main(String[] args) throws InterruptedException {
        Thread t1 = new Thread(() -> {
            for (int i = 0; i < 100; i++) {
                counter++; // read → modify → write: NO es atómico
            }
        });
        Thread t2 = new Thread(() -> {
            for (int i = 0; i < 100; i++) {
                counter++; // otro hilo hace exactamente lo mismo
            }
        });
        Thread t3 = new Thread(() -> {
            for (int i = 0; i < 100; i++) {
                counter++; // y otro más
            }
        });

        t1.start(); t2.start(); t3.start();
        t1.join();  t2.join();  t3.join();

        // Debería ser 300. Casi nunca lo es.
        System.out.println("counter = " + counter);
    }
}
La solución

Sincronización: proteger datos compartidos

Identificar una race condition es solo la mitad del trabajo. Java ofrece tres mecanismos para garantizar que el read-modify-write sea siempre atómico y seguro.

// Solución 1: synchronized block — el candado intrínseco de Java
public class SafeCounter {
    static int counter = 0;
    static final Object LOCK = new Object(); // el "monitor" compartido

    public static void main(String[] args) throws InterruptedException {
        Thread t1 = new Thread(() -> {
            for (int i = 0; i < 1000; i++) {
                synchronized (LOCK) {  // solo un hilo entra a la vez
                    counter++;         // read-modify-write ahora es atómico
                }                      // lock liberado automáticamente al salir
            }
        });
        Thread t2 = new Thread(() -> {
            for (int i = 0; i < 1000; i++) {
                synchronized (LOCK) {
                    counter++;
                }
            }
        });
        t1.start(); t2.start();
        t1.join();  t2.join();
        System.out.println("counter = " + counter); // siempre 2000 ✓
    }
}
1
Monitor object

Cada objeto Java tiene un monitor interno (lock intrínseco). Al entrar a synchronized(obj), el hilo adquiere ese monitor. Solo uno puede tenerlo a la vez — el resto queda en estado BLOCKED.

2
Sección crítica

El código dentro del bloque se llama sección crítica. Es la única zona donde el acceso al dato compartido está garantizado como atómico. El lock se libera al salir del bloque, incluso si hay excepción.

3
synchronized method

public synchronized void increment() es equivalente a synchronized(this). Usa la instancia como monitor — cómodo pero hace que toda la instancia sea el lock, lo que puede ser demasiado amplio.

¿Cuándo usarlo?

Cuando necesitás proteger múltiples operaciones como unidad (compound actions), o cuando operás sobre objetos sin versión Atomic. Tiene overhead por adquisición/liberación del monitor — para un contador simple, preferí AtomicInteger.

import java.util.concurrent.atomic.AtomicInteger;

// Solución 2: AtomicInteger — sin synchronized explícito
// Usa instrucciones CAS (Compare-And-Swap) del hardware → sin locks del SO
public class AtomicCounter {
    static AtomicInteger counter = new AtomicInteger(0);

    public static void main(String[] args) throws InterruptedException {
        Thread t1 = new Thread(() -> {
            for (int i = 0; i < 1000; i++) {
                counter.incrementAndGet(); // equivalente atómico de counter++
            }
        });
        Thread t2 = new Thread(() -> {
            for (int i = 0; i < 1000; i++) {
                counter.incrementAndGet();
            }
        });
        t1.start(); t2.start();
        t1.join();  t2.join();
        System.out.println("counter = " + counter.get()); // siempre 2000 ✓
    }
}

// Operaciones disponibles en AtomicInteger:
AtomicInteger n = new AtomicInteger(10);
n.get();                    // lee el valor actual
n.set(5);                   // setea el valor (atómico)
n.getAndIncrement();        // retorna el viejo, luego incrementa (≡ i++)
n.incrementAndGet();        // incrementa, luego retorna el nuevo (≡ ++i)
n.addAndGet(5);             // suma 5, retorna el nuevo valor
n.compareAndSet(10, 0);     // si n == 10, setea a 0. Retorna true si cambió
¿Cuándo usarlo?

Para contadores, flags y operaciones simples sobre un único valor. Más rápido que synchronized porque usa instrucciones CAS del hardware en vez de locks del SO. El paquete java.util.concurrent.atomic también ofrece AtomicLong, AtomicBoolean y AtomicReference<T>.

import java.util.concurrent.locks.*;

// Solución 3: ReentrantLock — control explícito y avanzado
public class LockCounter {
    static int counter = 0;
    static ReentrantLock lock = new ReentrantLock();

    public static void main(String[] args) throws InterruptedException {
        Thread t1 = new Thread(() -> {
            for (int i = 0; i < 1000; i++) {
                lock.lock();         // adquiere el lock explícitamente
                try {
                    counter++;
                } finally {
                    lock.unlock();   // SIEMPRE en finally — garantiza liberación incluso con excepción
                }
            }
        });
        t1.start();
        t1.join();
        System.out.println("counter = " + counter);
    }
}

// Ventaja clave: tryLock() previene deadlocks con timeout
boolean acquired = lock.tryLock(100, TimeUnit.MILLISECONDS);
if (acquired) {
    try {
        // sección crítica
    } finally {
        lock.unlock();
    }
} else {
    // no obtuve el lock en 100ms → tomo otra decisión en vez de bloquearme
    System.out.println("Timeout: no pude obtener el lock, continuando...");
}
¿Cuándo usarlo?

Cuando necesitás tryLock() con timeout para evitar deadlocks, locks de lectura/escritura con ReadWriteLock, o cuando synchronized no da el nivel de control requerido. El unlock() en finally es obligatorio — sin él el lock queda tomado para siempre.

Deadlock: el abrazo mortal

Un deadlock ocurre cuando dos o más hilos quedan bloqueados esperando recursos que el otro tiene — y ninguno puede avanzar. El programa se congela silenciosamente, sin error ni excepción.

// Deadlock clásico: dos hilos, dos locks, orden inverso
Object lockA = new Object();
Object lockB = new Object();

Thread t1 = new Thread(() -> {
    synchronized (lockA) {           // T1 toma lockA ✓
        try { Thread.sleep(50); } catch (InterruptedException e) {}
        synchronized (lockB) {       // T1 espera lockB... pero T2 lo tiene ☠
            System.out.println("T1: obtuve ambos");
        }
    }
});

Thread t2 = new Thread(() -> {
    synchronized (lockB) {           // T2 toma lockB ✓
        synchronized (lockA) {       // T2 espera lockA... pero T1 lo tiene ☠
            System.out.println("T2: obtuve ambos");
        }
    }
});

t1.start();
t2.start();
// ☠ El programa se cuelga aquí — espera circular infinita

Cómo evitarlo
Orden consistente de locks

Siempre adquirir los locks en el mismo orden en todos los hilos. Si T1 y T2 ambos hacen lockA → lockB, no hay deadlock posible.

tryLock() con timeout

lock.tryLock(100, TimeUnit.MILLISECONDS) — si no obtenés el lock en 100ms, salís y liberás lo que ya tenés. Rompe la espera circular.

Colecciones concurrentes

ConcurrentHashMap, BlockingQueue y el resto del paquete java.util.concurrent manejan sincronización internamente — sin locks manuales, sin riesgo de deadlock.

La sintaxis de la concurrencia

Tres formas de crear hilos en Java

Java evolucionó la API de hilos a lo largo de las versiones. Cada enfoque tiene su contexto ideal — saber cuál usar es parte del criterio profesional.

// Opción 1: Extender Thread
public class MiHilo extends Thread {
    private String nombre;

    public MiHilo(String nombre) {
        this.nombre = nombre;
    }

    @Override
    public void run() {
        // Este código corre en un hilo separado
        for (int i = 1; i <= 5; i++) {
            System.out.println(nombre + " → paso " + i);
            try {
                Thread.sleep(200); // simula trabajo
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                return;
            }
        }
    }
}

// En main():
MiHilo h1 = new MiHilo("Hilo-A");
MiHilo h2 = new MiHilo("Hilo-B");
h1.start(); // NO llamar run() — start() crea el hilo real
h2.start();
h1.join(); h2.join(); // esperar a que terminen
¿Cuándo usarlo?

Código educativo o scripts simples donde necesitás control total sobre el hilo. En producción, evitalo — extender Thread limita la herencia de otras clases y no escala bien.

// Opción 2: Implementar Runnable (preferida sobre Thread)
public class MiTarea implements Runnable {
    private String nombre;

    public MiTarea(String nombre) {
        this.nombre = nombre;
    }

    @Override
    public void run() {
        for (int i = 1; i <= 5; i++) {
            System.out.println(nombre + " → paso " + i +
                " [" + Thread.currentThread().getName() + "]");
        }
    }
}

// Con lambda (Java 8+) — más limpio y conciso
Runnable tarea1 = () -> {
    for (int i = 0; i < 5; i++) {
        System.out.println("Lambda hilo: " + i);

Thread hilo1 = new Thread(new MiTarea("Worker-1"));

¿Cuándo usarlo?

Cuando la tarea es una unidad de trabajo discreta. Permite implementar otras interfaces al mismo tiempo. Las lambdas lo hacen muy conciso. Mejor que extender Thread — separa la tarea del mecanismo de ejecución.

// Opción 3: ExecutorService — el estándar en producción
import java.util.concurrent.*;

public class EjecutorDemo {
    public static void main(String[] args) throws Exception {
        // Pool de 4 hilos reutilizables
        ExecutorService executor = Executors.newFixedThreadPool(4);

        // Enviar tareas sin preocuparse por la gestión de hilos
        for (int i = 1; i <= 10; i++) {
            final int tarea = i;
            executor.submit(() -> {
                System.out.println("Tarea " + tarea +
                    " en " + Thread.currentThread().getName());
                return tarea * tarea;
            });
        }

        // Esperar a que todas las tareas terminen
        executor.shutdown();
        boolean terminado = executor.awaitTermination(10, TimeUnit.SECONDS);
        System.out.println("Completado: " + terminado);

        // Con Callable para obtener resultados tipados
        ExecutorService exec2 = Executors.newSingleThreadExecutor();
        Future<Integer> futuro = exec2.submit(() -> {
            Thread.sleep(500);
            return 42;
        });
        int resultado = futuro.get(); // bloquea hasta tener el valor
        System.out.println("Resultado: " + resultado);
        exec2.shutdown();
    }
}
¿Cuándo usarlo?

Siempre que sea posible en código real. Reutiliza hilos, controla el pool size, maneja excepciones correctamente y soporta Callable/Future para resultados. Es el estándar de la industria desde Java 5.

Código para copiar — Race Condition Demo 
public class RaceConditionDemo {
    // volatile: fuerza lecturas/escrituras en RAM real (sin cache en registros CPU)
    // PERO no garantiza atomicidad del read-modify-write — la race sigue ocurriendo
    static volatile int counter = 0;

    public static void main(String[] args) throws InterruptedException {
        int HILOS = 3;
        int INCREMENTOS = 200;
        Thread[] threads = new Thread[HILOS];

        for (int t = 0; t < HILOS; t++) {
            final int id = t + 1;
            threads[t] = new Thread(() -> {
                for (int i = 0; i < INCREMENTOS; i++) {
                    int temp = counter;   // PASO 1: READ — lee el valor actual
                    Thread.yield();       // fuerza context switch aqui (el scheduler puede interrumpir)
                    counter = temp + 1;  // PASO 2: WRITE — otro hilo pudo leer el mismo valor entre medio!
                }
            }, "Thread-" + id);
        }

        long inicio = System.currentTimeMillis();
        for (Thread t : threads) t.start();
        for (Thread t : threads) t.join();
        long fin = System.currentTimeMillis();

        int esperado = HILOS * INCREMENTOS;
        System.out.println("=== Race Condition Demo ===");
        System.out.println("Resultado:  " + counter);
        System.out.println("Esperado:   " + esperado);
        System.out.println("Perdidos:   " + (esperado - counter) + " incrementos");
        System.out.println("Tiempo:     " + (fin - inicio) + "ms");

        if (counter == esperado) {
            System.out.println("Tuviste suerte esta vez. Corre de nuevo.");
        } else {
            System.out.println("Race condition confirmada: " + (esperado - counter) + " incrementos se perdieron.");
        }
    }
}

Vocabulario técnico

Glosario

Tocá cada tarjeta para ver la definición. Estos son los términos que vas a usar en entrevistas técnicas, revisiones de código y diseño de sistemas concurrentes.

Proceso Tocá

Instancia de un programa en ejecución con su propio espacio de memoria aislado. Tiene código, heap, stack y recursos propios. El SO le asigna un PID único. Ej: cada pestaña del navegador es un proceso.

Hilo (Thread) Tocá

Unidad de ejecución dentro de un proceso. Comparte heap y código con otros hilos del mismo proceso pero tiene su propio stack. También llamado "proceso liviano". Java crea hilos con Thread o ExecutorService.

Scheduler Tocá

Componente del SO que decide qué hilo recibe tiempo de CPU y por cuánto tiempo. Java no controla al scheduler — el SO es el árbitro. Por eso el orden de ejecución de los hilos no está garantizado.

Concurrencia Tocá

Múltiples tareas en progreso simultáneo, intercaladas por el scheduler en uno o más cores. Es un concepto de diseño: el programa está estructurado para manejar múltiples tareas a la vez, aunque no corran exactamente al mismo tiempo.

Paralelismo Tocá

Ejecución verdaderamente simultánea de múltiples tareas en múltiples cores. Requiere hardware (más de 1 core) y software bien particionado. Un programa con un solo core puede ser concurrente pero nunca paralelo.

Race Condition Tocá

Bug donde el resultado de un programa depende del orden de ejecución de los hilos. Ocurre cuando dos o más hilos acceden y modifican datos compartidos sin sincronización. El resultado es impredecible y difícil de reproducir.

Context Switch Tocá

Operación del SO donde guarda el estado de un hilo (registros, stack pointer, program counter) y carga el estado de otro. Dura ~1000ns. Demasiados context switches pueden degradar el rendimiento más que el trabajo real.

ExecutorService Tocá

API de alto nivel de Java para gestionar pools de hilos. Reutiliza hilos en lugar de crear y destruir, controla el tamaño del pool, maneja excepciones y soporta Callable/Future para tareas con resultados. Estándar desde Java 5.

Antes de arrancar

¿Cómo se investiga una race condition?

Una race condition no es un error que se ve a simple vista. Aparece de forma intermitente, con valores incorrectos que varían entre ejecuciones. La clave es reproducirla consistentemente y luego corregirla con la herramienta de sincronización correcta.

En Java, la solución básica es synchronized. La solución de alto nivel es AtomicInteger del paquete java.util.concurrent.atomic. Ambas garantizan atomicidad del read-modify-write.

Reproducí y solucioná la race condition

Paso 1 — Implementá el contador sin sincronización

Creá una clase RaceCounter con un int counter estático. Usá 3 hilos, cada uno con 1000 incrementos. Ejecutá 5 veces y anotá los resultados. El valor debería ser 3000 pero no lo será.

Paso 2 — Corregí con AtomicInteger

Reemplazá el int counter por AtomicInteger counter = new AtomicInteger(0) y usá counter.incrementAndGet(). Verificá que ahora siempre da 3000.

Paso 3 — Medí el impacto en rendimiento

Usá System.currentTimeMillis() para medir el tiempo de ambas versiones con 10 hilos × 10.000 incrementos. Documentá la diferencia y explicá por qué existe.

Paso 4 — Documentá tus hallazgos

Entregá: el código de ambas versiones, una tabla con los resultados de al menos 5 ejecuciones de cada versión, y un párrafo explicando por qué ocurre la race condition en términos del ciclo read-modify-write.
